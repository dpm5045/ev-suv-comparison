Architecture Assessment & Improvement Plan

ThreeRowEV.com · July 7, 2026

Overall Verdict

The architecture is fundamentally sound and well-matched to the product: a static JSON dataset rendered through Next.js SSG, URL-driven filter state, and statically generated SEO pages per vehicle and comparison pair. The standout design win is the lib/spec-fields.ts registry — one file driving five rendering surfaces. Security headers, JSON-LD (Product + FAQ), and the validate/refresh tooling are all above par. The weaknesses are mostly drift and duplication accumulating around a solid core.
Priority 1 · SEO

SEO Architecture — Highest-Leverage Gap

Given the monetization plan depends on organic traffic, this is where structural work pays off most. It also directly addresses the "discovered – currently not indexed" issue in Search Console.

  • Promote tabs to real routes. All main tabs live behind ?tab= on /, so Google effectively sees one page for Overview, Comparison, Spec & Select, Side-by-Side, and Glossary. Move them to /comparison, /side-by-side, /glossary, etc. with static shells and canonical URLs; keep query params for filters only.
  • Fix the frozen sitemap date. app/sitemap.ts hardcodes lastModified: 2026-03-19 despite four data refreshes since. Derive it from a last_updated field in ev-data.json and bump it inside the /refresh skill.
  • Add /explore to the sitemap — it's missing entirely.
Priority 2 · Drift

Vehicle Visual Identity Defined in Four Diverging Places

Badge and chart colors live in VEHICLE_CLASSES + globals.css (dark and light variants), app/og/route.tsx, DataExplorer.tsx, and MarketInsights.tsx — the last two with different hex values, and each holding only ~12 of the 20 vehicles. Tesla Model Y L, Toyota Highlander EV, Lexus TZ, and Subaru Getaway silently render gray #888 in charts today. This violates the project's own "derive from DATA, no hardcoding" rule in spirit.

Fix: a single lib/vehicle-theme.ts exporting { vehicle → cssClass, hexDark, hexLight }, with badge CSS emitted as custom properties from the same source. Adding a vehicle becomes a true single-file edit again.

Related: MarketInsights sets Chart.js global defaults to dark-theme colors at module scope (ChartJS.defaults.color = '#9898b0') — verify chart legibility in light theme; it is likely broken.

Priority 3 · Data Model

Stringly-Typed Data Taxes Every Consumer

Nearly every numeric field is number | string | null, forcing typeof guards in every renderer, and parsePrice() regex-parses display strings like "$45,000–$52,000" to do math (duplicated in OverviewTab and ComparisonV2Tab).

  • Store structured values, derive display strings — e.g. preowned_low / preowned_high numbers plus an optional status note, formatting the range at render time.
  • Compute OTD at load time instead of storing it. The formula is fixed — storing the result is why the checklist has a manual "recalculate OTD" step.
  • Derive the preowned array from details where duplicated; the sync requirement exists only because of the duplication.
  • Run scripts/validate-data.js in the build (prebuild step) so a bad refresh can't deploy. The validator is good; it currently only runs when someone remembers.
Priority 4 · Dependencies

Consolidate to One Chart Library

The app ships both chart.js + react-chartjs-2 (MarketInsights) and @observablehq/plot + full d3 (DataExplorer). The dynamic import softens the blow, but full d3 is heavy when Plot already bundles what it needs, and two libraries means two theming systems. Observable Plot can express MarketInsights' bar/scatter charts; converging on one drops a dependency family and halves the chart theming surface.

Priority 5 · Smaller Items

Smaller but Real

  • Filter history spam: updateParams uses router.push for every filter change, so the back button steps through each checkbox click. Use replace for filter refinement; reserve push for tab changes.
  • Bucket filters aren't shareable: MSRP/Range/HP buckets in ComparisonV2Tab are local useState while all other filters are URL params — those URLs don't round-trip, contradicting the design intent.
  • globals.css is a 3,213-line monolith with sections already marked "legacy." Prune dead sections; extract the biggest self-contained blocks before it hits 5k lines.
  • No tests despite Playwright being installed. A handful of smoke tests (each tab renders, a vehicle page renders, filters produce results) plus validate-data in CI would catch the real regression classes: data-shape breakage and render drift.
  • Repo hygiene: the root has untracked report HTMLs, a PDF, screenshots, and tsconfig.tsbuildinfo. Move reports to docs/, gitignore *.tsbuildinfo.
No Change

Explicitly Keep As-Is

The spec-fields.ts registry pattern, URL-as-state for shareable filters, the dual table/card responsive render, SSG vehicle/compare pages with generated FAQ JSON-LD, the security headers in next.config.mjs, and the skills-driven data refresh workflow. The disabled news API stub is the right call versus dead code.

Roadmap

Sequenced Plan

1
SEO routes + sitemap fixes Medium Promote tabs to real routes with canonicals; derive sitemap lastModified from the data; add /explore. Directly serves the traffic goal.
2
Vehicle theme consolidation Small Single lib/vehicle-theme.ts source of truth for badge classes and chart colors; verify light-theme charts. Cheap, and stops active drift.
3
Data model refactor + build-time validation Large Structured price fields, computed OTD, derived preowned array, validator wired into the build so the change lands safely.
4
Chart library convergence Medium Port MarketInsights to Observable Plot (or DataExplorer to Chart.js); drop the other dependency family.
5
Hygiene sweep Small History push→replace, bucket filters to URL params, CSS pruning, Playwright smoke tests, repo cleanup.
